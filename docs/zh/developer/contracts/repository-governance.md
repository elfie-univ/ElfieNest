# 仓库架构治理契约

**契约版本：** 1.15
**采用日期：** 2026-08-12
**修订日期：** 2026-08-20
**机器约束范围：** 全仓变更分类与架构边界

本契约定义 ElfieNest 如何组织、修改和执行架构规则。精确基线和一致性台账只在仍有
已登记架构缺口时存在。已经清零的规则集由永久 deny-all Scanner 和测试直接执行；
即使通用基线已经退役，活动子一致性台账仍可记录未由该基线表达的语义或结构缺口。

## 四类文档

| 目录 | 含义 | 生命周期 |
| --- | --- | --- |
| `architecture/` | 描述当前系统的说明性地图 | 持续更新，不具规范权威 |
| `contracts/` | 版本化的所有权、依赖和边界规则 | 长期保留，只能有意修改 |
| `conformance/` | 精确的临时缺口和迁移门槛 | 缺口与基线清零后删除 |
| `decisions/` | 已接受的架构决策记录 | 作为决策历史长期保留 |

英文与简体中文镜像必须同步。讨论笔记、未完成方案和实现清单不能变成契约。

## 质量治理体系

架构质量由一套相互连接的机制共同维护：

| 机制 | 目的 | 生命周期 |
| --- | --- | --- |
| 契约 | 定义长期所有权、依赖和 authority | 永久 |
| ADR | 解释有意契约变更及被拒绝方案 | 永久 |
| 根/子 `AGENTS.md` | 把契约转成编码 Agent 的本地执行指引 | 边界存在期间永久 |
| Scanner、类型/Lint 与架构测试 | 执行可机器证明的规则 | 永久 |
| 精确旧架构基线 | 棘轮式缩减已知实现债，不授权新增债 | 临时 |
| 一致性台账 | 命名每个临时缺口和删除门槛 | 临时 |
| CI 主分支比较与维护者审查 | 防止变更放松评判自己的规则 | 永久 |
| Runtime 健康与 Observer 投影 | 报告运行健康，与源码架构检查分离 | 永久 |
| 分级验证与按检查复用 | 按改动风险匹配本地成本，不重复已经证明的昂贵检查 | 永久 |

任何单一机制都不能替代其他机制。契约声明目标，`AGENTS.md` 指导执行，机器门拒绝可
检测违规，一致性台账和基线只记录旧债，人工审查覆盖无法完全机器证明的语义规则。

## 分级验证与按检查复用

验证根据改动路径的影响范围选择；高风险结果可以升级验证级别，但不能降级：

每个级别都先执行格式与静态分析快线；在任何测试、构建、文档构建或其他昂贵检查开始前，
快线必须已经通过。本地提交候选冻结前，准备步骤可以用 Ruff formatter 写入，但只能处理
本次选中范围内 dirty 或 untracked 的 `.py` 和 `.pyi` 文件。同一选中文件同时具有 staged
与 unstaged 改动时必须拒绝自动格式化。Commit Hook、测试和 CI 只能检查，不能修改候选文件。

| 级别 | 触发条件 | 必须执行 |
| --- | --- | --- |
| G1 提交 | 普通本地改动 | 快线证据、暂存文件密钥扫描和受影响测试 |
| G2 推送 | 功能分支推送或受影响的集成路径 | G1，加质量基线，以及受影响的 API、持久化、架构或文档集成检查 |
| G3 主线 | 主线合并/发布、治理/工具链改动或影响未知 | 当前候选检查和一次必需的昂贵后盾 |

候选分类器负责升级判断。未知可执行路径、治理、工具链、锁文件和交付路径改动都升级
到 G3。普通提交不再默认等待 G3，只有自身影响要求升级时才执行；G3 仍是受保护主线的
最终后盾。

同一次所选级别调用中，全仓质量基线最多执行一次。G1 和 Commit Hook 不执行它；G2/G3
按需直接调用，不能再通过总括 Hook 重复调用。

Main 后盾在对应 `node_modules/.modules.yaml` 存在、且 package manifest 与 lockfile 相对基础
提交未变化时复用现有 pnpm 安装。只有缺少这份证明或任一输入发生变化时才允许安装依赖；网络
安装失败必须停止门禁，不能升级或重试更宽的验证级别。

只有成功的确定性测试检查可以按检查复用。交付级别只是一组必需检查，不属于单项测试检查
身份；证据键
覆盖检查/规则版本、精确命令、声明输入的内容与文件模式、本机工具指纹，以及选择依赖的
不可变基础提交。因此 G1 已经执行且输入未变的聚焦测试会被 G2 直接复用，不会再次启动。

本地 G3 pytest 后盾拆成已注册的顶层稳定测试包。每个包先保守声明源码、测试、配置和共享
fixture 输入，再从包内测试与 `conftest.py` 推导本地 Python 的传递 import 闭包；动态或非
Python 入口仍必须显式声明。未知可执行输入会使所有包失效。只有通过记录、覆盖率片段、产物
摘要、coverage/pytest 版本和可读的覆盖率数据全部一致时才可复用。此前通过受控运行器完整
执行同一个测试包，会产生同一份证据，因此 G3 会跳过它；更窄的 node、单文件或任意 selector
不能冒充完整包。同一次运行的各测试包共享一份仓库内容快照，并在接受缓存命中前复核输入
签名。G3 最后合并当前所有包的覆盖率片段，并只在合并后执行一次全仓覆盖率阈值；合并失败
会使涉及的覆盖率片段失效。直接运行原始 `pytest` 仍可用于诊断，但不会进入复用证据库。

精确候选证据仍可复用整个级别；G3 还记录独立昂贵后盾指纹，覆盖所有改动的源码、测试、
依赖、工具链、普通文档和验证规则输入。除缓存规则明确认定的生成物或忽略路径外，所有
改动路径都必须进入指纹；无法分类的路径一律 fail-closed。

失败、阻塞、超时和真实 Provider 结果永远不能作为通过结果缓存；同键强制重跑失败时，
旧通过记录也会被删除。内部 `--direct-main` 路径会执行完整后盾但保留有效测试包证据；
`--no-cache` 只禁止读取所选级别已要求检查的有效证据，不能改变级别或增加更广检查。
一个 G3 测试包失败后，更早通过的包记录仍有效；下一次调用会跳过这些记录，从失败或
尚未运行的包继续。
快线失败时必须在任何测试或昂贵检查启动前停止。后续修复循环先只重跑精确失败 node，
再扩大到所属测试文件或模块，再到受影响集成检查。失败不能自动重启更广门禁或已经证明
的检查；只对最终可执行候选运行一次必需的 G3 后盾，不在每次编辑后重新启动全套。
每次扩大必须有新增依赖或风险理由。
每次复用或执行门禁后都再次计算工作区指纹；期间发生变化就丢弃结果。缓存只写入被忽略的
`build/validation-cache/`，不得包含源码、凭据或用户数据。GitHub 状态检查仍必须针对最新
commit SHA 通过，本地证据不能替代新 SHA 的 CI 检查。

架构依赖按有效目标定义，不只按 `import` 语句定义。通过 `python -m`、脚本路径、
subprocess、Node 子进程命令、Shell 命令、`importlib`、`runpy` 或其他动态加载器到达
仓库模块时，必须遵守与静态 import 相同的所有权和允许方向矩阵。有效依赖 Scanner
覆盖仓库自有 Python、Node、Godot、Shell 执行表面和新出现的源码根，同时按调用方与
目标的模块所有权分类，不为当前某个违规目录写黑名单。无法静态解析的目标仍须通过
强类型 Port 或 Bootstrap 所有的启动计划，并由人工审查。

## 实现证据与交付声明

已经批准的设计或契约就是实现的固定目标。证据记录在对应的一致性台账、变更说明、测试
结果或运行产物中；这些记录都不能成为第二个架构事实源。

测试、构建成功、工作区干净和提交成功只能证明各自的检查，不能替代目标要求的真实启动、
关闭、崩溃、并发、安装、跨平台、压力或 Provider 验证。当前环境无法执行必需检查时，
交付报告必须保留阻塞状态，写明缺失环境和下一步证据。最终交付必须分别报告已完成、保留
和阻塞项，并给出可重放的命令或场景证据。外部环境缺口在 CI 或匹配主机提供证据前保持
开放；不存在把它变成完成状态的本地参数。

## 端到端治理流程

每个涉及架构的变更都遵循同一条可见闭环：

1. 改代码前先读最近的 `AGENTS.md`、权威契约和当前一致性条目；
2. 把工作分类为治理变更或产品/迁移变更；
3. 治理变更只调整 ADR、契约、本地指引和机器规则，不带实现侧文件；迁移变更固定目标，
   一次只选择一个完整能力或业务域切片；
4. 本地使用候选 Scanner 对照候选精确基线，并运行聚焦架构测试；
5. CI 对 Pull Request 和受保护分支 Push 都使用基础提交中的不可变 Scanner 检查候选
   生产代码，再要求维护者审查；
6. 迁移真实调用链通过后，删除旧实现，只减少对应基线条目，只关闭已有证据的台账项；
7. 某规则集最后一个缺口清零后，把具备证据的台账标记为待收口，并立即执行下述独立
   “零债务治理收口流程”；全 closed 台账或空基线不能成为稳定状态。

`scripts/architecture/contract_registry.py` 中的机器可读注册表把每个契约版本与
中英文镜像、ADR、本地规约、Scanner、架构测试、一致性台账和旧债基线关联。架构测试
会拒绝无所属契约的测试文件和缺失的注册产物。静态分析无法证明的语义仍由人工审查负责。

## 清理证明与完成声明

测试通过、构建成功、工作区干净或推送成功，只能证明各自结果，不能证明批准的清理或
迁移已经完成。声明“清理完成”或“符合契约”前，负责审查必须：

1. 明确本次清理对应的契约条款、一致性行及文件系统/运行范围；
2. 递归盘点该范围内已跟踪、未跟踪、被忽略和空路径，并与获批准目标归置逐项对比；
3. 把每个路径归类为目标源码、保留内容、开发输入、生成物、当前已登记债务或已经证明
   可删除的候选；
4. 按需追踪静态 Import、动态启动、CLI、场景/资源、导出、文档和外部消费者引用；
5. 分开报告已完成、保留和剩余项，再运行相关 Scanner 及正向/反向行为检查。

只要存在未分类路径或受影响的一致性行仍 open，即使选中的测试全部通过，完成声明仍是
错误的。受契约保护的清理根目录使用永久结构分类：未知直接条目失败；开放行拥有的临时
路径可以缩减或修改，但不能新增文件。

一致性行第一次标记为 `closed` 时，必须在一个简洁证据单元格中同时具备五个机器稳定
字段：`target=`、`inventory=`、`references=`、`verification=` 和 `residuals=`。测试
不能单独提供全部字段；人工审查其真实性，基线感知治理检查器验证字段存在、双语状态
一致及状态变化。

## 本地执行规约

根 `AGENTS.md` 是仓库入口。在可能反转依赖、泄漏 authority、绕过持久化规则或削弱
机器治理的所有权边界，必须放置子 `AGENTS.md`。子规则只能细化父契约，不能反转；
普通叶子目录不复制仪式性文件。

系统契约由根 `AGENTS.md` 摘要，并在 Elfie、Nest 和高风险所有权边界细化。App 契约由
`app/AGENTS.md` 摘要，并在 App 各区域以及 lifecycle、embodiment、devices、API、
Desktop、CLI、Setup、accounts、configuration、persistence、
架构 Scanner 和架构测试等高风险边界细化。

## 变更类别

每个受审查的 Commit 或 Pull Request 只能属于以下一类：

1. **产品或迁移变更。** 可以修改实现侧文件并缩减已有架构基线。实现侧包括产品代码、
   Developer Tools、构建/发布脚本、普通测试、可执行 Manifest、交付 Workflow 和
   文档站代码，但不能修改规范性契约、治理规则、扫描器或 CI 策略。
2. **治理变更。** 可以修改契约、`AGENTS.md`、架构扫描器、治理 CI 和 ADR，但不能
   修改实现侧文件。

禁止混合两类变更。说明公开产品行为所需的普通文档可以与产品代码同行，但修改架构
契约或执行方式仍必须单独治理。这样同一个变更不能先放松题目，再让自己的实现过关。

## 契约变更流程

有意改变所有权、依赖或 authority 时，必须同时满足：

1. 先接受一份说明背景、选项、决策和后果的 ADR；
2. 同步升级中英文契约版本；
3. 执行指引变化时同步修改根或子 `AGENTS.md`；
4. 可机器检查的规则同步修改扫描器和聚焦架构测试；
5. 使用只含治理内容的 Pull Request 并经过维护者审查；
6. 若实现也要变化，另开后续产品迁移变更。

ADR 不能批准无限期例外。临时实现缺口必须具有一致性 ID、精确机器条目和删除条件。

全仓宏观架构正式冻结为 v1。以后若要改变顶层模块所有权、authority、依赖方向、生产
组合/生命周期所有权或系统级 Port 语义，必须先建立新的独立 ADR，同步升级契约版本，
并使用不含产品实现的治理专用提交；修改旧 ADR 不能批准新的宏观架构决策。

架构 Scanner、架构测试和治理 CI 只能在治理专用提交中修改，并同步更新一份解释规则
变化的双语 ADR。若同时改变契约本身，还必须执行上述契约版本流程。

## 渐进迁移与持续可运行

契约描述最终目标，并不要求当前代码一次性到达。当前违规只有在已经登记于一致性台账
和精确基线时才能暂存；不得复制到新代码，也不能作为新增同类实现的先例。

每个迁移切片都必须保证主分支上的应用可构建、可测试、可使用。安全顺序是：定义目标
Facade/Port 和强类型模型，实现 Adapter，由 Bootstrap 装配，迁移完整生产调用方，
证明至少一条真实链路，然后删除旧实现并缩减基线。半条调用链不能合入主分支。

在调用方切换期间，新旧实现可以在一个尚未合并的迁移切片中短暂共存，但同一事实仍然
只有一个活动 authority。双写、Fallback Read 和兼容 Alias 必须单独批准并具有删除门，
不是默认迁移手段。一个能力无法安全地在单个切片完成时，应在稳定 Port 或 Facade 边界
进一步拆分，而不是让提交之间的 Runtime 行为失效。

## 主分支对照棘轮

App 与系统架构 CI 使用 Pull Request 基础提交或受保护分支 Push 前提交中的不可变事实
检查候选代码：

- 使用主分支扫描器扫描候选生产代码；
- 候选违规必须已经存在于主分支基线；
- 候选扫描器必须与候选基线精确一致；
- 无基线的有效依赖 Scanner 必须报告零个禁止的仓库目标；
- 普通变更只能删除基线条目，不能新增或改写；
- 治理变更不得修改旧架构基线；
- 治理文件和实现侧文件不能在同一变更中出现；
- 删除路径必须参与变更分类与收口校验；
- 临时清理路径不能新增基线树中不存在的文件；
- 一致性状态和注册项变化必须对比基线双语台账，不能只观察候选文件。

实现侧分类覆盖全仓并采用 fail-closed。识别治理产物和普通说明文档后，其余所有被跟踪
文件都属于实现侧，包括产品、Developer Tools、脚本、测试、根 Runtime/工具链配置、
Manifest、资产、文档站代码和非治理 Workflow。架构 Scanner 和测试的治理身份优先；
普通说明文档保持中立，可以随其描述的变更类别同行。新增目录、后缀或可执行表面不能
因为未分类而绕过门禁。

因此，修改当前分支的 Scanner、契约或基线都不能放过新增生产违规。首次引入门禁的
Bootstrap 变更因为基础提交没有治理契约，可以创建初始精确基线；它进入受保护主分支
后，主分支 Scanner 缺失即报错，新增或改写基线也会被拒绝。

CI 也会在受保护分支被直接 Push 后执行比较，使绕过行为立即可见；但只有仓库分支保护
才能在写入前阻止这次 Push。因此受保护主分支禁止直接 Push，并要求合并前通过本门禁。

## 零债务状态

最后一笔产品/迁移变更负责删除最后一个生产违规和最后一个精确基线条目，用五类证据
关闭最后一行，并把两份全 closed 镜像标为 `收口状态：ready`，但不修改治理规则。这个
短暂的已注册待收口状态只用于交接给紧随其后的独立治理收口变更，后者必须原子完成：

1. 检查当前活动工作区，删除包括空目录、未跟踪目录和被忽略目录在内的全部退役物理
   路径，再以 deny-all 模式运行永久 Scanner 和聚焦架构测试；
2. 运行每个待关闭契约在注册表中拥有的全部架构测试；同时关闭多个契约时必须运行完整
   `test/architecture/`，不得使用人工选择的子集；
3. 删除空基线和全 closed 的中英文一致性台账；
4. 删除注册表字段、硬编码测试绑定、索引和链接；
5. 把根/子 `AGENTS.md` 中的临时迁移指引替换为长期目标边界和防回退规则；
6. 搜索已退役缺口 ID、失效链接和迁移期术语，只有明确表达历史背景的 ADR 可以保留；
   永久防重建测试可以保留已退役基线的路径；
7. 删除临时产物后复跑同一组 Scanner 和必需架构测试，再验证双语镜像、注册表所有权
   和 CI deny-all 行为。

只要还存在空基线、已注册的待收口台账、退役物理路径、过期局部指引、要求已退役债务
产物存在的测试，或任一契约拥有的架构测试尚未通过，收口就不完整。注册表测试只允许
明确 ready 且每行证据完整的全 closed 台账，仍拒绝已注册空基线。基线检查器纳入删除，
拒绝删除开放、证据不足、只删一种语言或混入产品文件的台账。永久 Scanner 与架构测试
继续保留；CI 全量测试覆盖完整架构套件，对任何检测条目直接失败，不在其他 Job 重复
同一套件。

不得为了容纳回退重新创建基线；只有具有已接受 ADR 的独立治理变更，才能修改底层契约
和 Scanner。

只有映射到某一致性条目的全部 Baseline 规则清零、全部临时结构路径消失且五类证据完整
后，该条目才能标记为 `closed`。机器测试拒绝仍有精确 Baseline 条目或临时路径的
`closed` 状态；人工审查继续判断所引用目录、线路和行为证据是否语义充分。

## 所有权与仓库外部设置

受保护主分支必须要求架构治理 CI 通过，并要求治理变更至少经过一名维护者审查。
仓库所有者确认有效 GitHub 团队账号后可以增加 CODEOWNERS；本契约不虚构不存在的
账号。分支保护和审查者身份属于仓库设置，无法只凭源码文件证明。
