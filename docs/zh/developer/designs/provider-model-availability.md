## 1. 目标与边界

本文设计 ElfieNest 如何配置本地或远程 Provider、加载真正有用的 Endpoint 模型、获得
具体连接下的模型能力、用最少的额外模型调用验证可用性、持续维护最新证据，并向 Owner
页面和其他应用服务提供统一状态。

本文不测试模型智力，不从私人聊天推断模型质量，不在未获用户同意时安装或下载大型本地
模型，也不允许业务代码自行拼接任意 Provider Payload。

核心区分是：

- 目录回答“可以选择哪些模型”；
- Endpoint 模型配置回答“当前连接下的这个模型支持什么”；
- 证据回答“什么时候实际观察到了什么”；
- 可用性回答“它现在能不能用”；
- 服务范围回答“它坏了是否影响当前运行中的产品”。

## 2. 事实层与权威

| 事实 | 含义 | 权威来源 |
| --- | --- | --- |
| Provider 产品 | 不含凭据的协议、认证、发现策略和 Adapter 默认配置 | 版本化 Provider 目录 |
| Provider 连接 | 一个账号、订阅或本地 Endpoint，以及凭据引用和生命周期 | Provider 连接存储 |
| Endpoint 模型 | 精确 `(connection_id, endpoint_model_id)` 的身份、元数据和请求配置 | 连接模型清单 |
| 证据 | 不可变的验证与真实执行观测 | Report Repository |
| 引用保护索引 | 包含未上线 Food 在内的全部模型引用，用于保护修改和删除 | 全部持久化消费者引用的派生投影 |
| 在用 Food 索引 | 当前可能获得生产流量的 Food 和角色 | Food 生命周期、Elfie 选择与生产决策的派生投影 |
| 可用性 | 当前可解释的 Provider/模型状态 | 以上事实的读取时投影 |

动态可用性、延迟和错误不能写回 Provider 配置。Canonical Model 身份只能帮助补全对比
信息，不能判定某个模型在某个 Provider 下是否支持某项能力。最终能力和可用性单位始终是
具体 Endpoint 模型。

内置 Provider 与模型目录是登记文档：`config/models/provider-catalog.yaml` 和
`config/models/model-catalog.yaml`。Runtime 代码必须通过
[配置管理契约](../contracts/configuration-management.md)定义的类型化配置边界加载；包内副本
不能成为回退 Authority。

## 3. Provider 配置与模型加载

### 3.1 配置流程

已知产品只要求可选别名和必要凭据；Base URL、协议、认证和发现策略来自产品配置。
自定义兼容 Endpoint 才展开这些高级字段。

自定义 Endpoint URL 必须先通过产品出站网络策略，之后才能发送凭据。除 Owner 明确批准
的本地或局域网 Provider 模式外必须使用 HTTPS；Link-local 和云元数据地址始终拒绝，
并且重定向绝不能把凭据转发到不同 Origin。

保存连接按以下顺序执行：

1. 先保存可继续修改的连接和凭据引用，后续失败也不能删除；
2. 做不产生模型输出的 HTTPS/API 可达性检查；产品存在合适接口时同时验证认证；
3. 加载并合并该产品专属模型清单；
4. 使用指定代表模型执行一次极小文本请求；
5. 展示清单、证据时间和可操作结果。

网络可达不等于模型可用。没有免生成认证接口时，系统只能得出 `reachable`，账号可用性
必须等到真实模型请求成功后才能确认。

### 3.2 模型清单来源顺序

Endpoint ID 取第一个可用的索引来源：

1. 带认证的产品专属官方清单或官方 Adapter；
2. ElfieNest 维护的版本化远程精选目录；
3. 随应用发布的内置精选目录；
4. 受保护的手工输入。

权威接口成功返回零个有权限模型时，这是“权威空清单”，不是发现失败。低优先级目录可以
继续显示明确标注的推荐候选，但不能声称当前账号拥有这些 Endpoint。只有所有必需分页都
成功完成，并由 Adapter 确认响应完整后，本次刷新才能参与“模型缺失”判断。

只有产品配置明确声明某个通用 `/models` 是该订阅的权威清单时才能使用。平台级大清单
不能冒充订阅清单。低优先级目录只有在元数据明确属于当前产品/Endpoint 时才能补全，
并且不能替换高优先级来源提供的 ID。通用 Canonical Model 记录只能帮助归组和展示，不能
为具体连接 Endpoint 填写最终上下文限制、能力或请求参数。

远程目录必须通过 Schema、版本以及签名或完整性固定校验，且绝不能包含凭据。发现
Adapter 必须限制响应字节数和记录数量；超限结果按发现失败处理并回退精选来源，不能静默
截断后伪装成权威清单。

正常页面只展示精选、手工和当前被引用模型的并集。真正权威的官方清单中额外出现的 ID，
可以放进折叠的“其他已发现”搜索区，但在被选择或引用前不进入卡片计数和自动验证。庞大的
原始发现结果只是诊断输入，不能不加筛选地展示或持久化成普通模型列表。

### 3.3 Endpoint 元数据与请求配置

每个 Endpoint 模型保存以下稳定或低频变化事实，并记录来源、目录版本和更新时间：

- Endpoint ID、显示身份、来源和最后发现状态；
- 上下文窗口和最大输出；
- 文本、视觉、工具、推理和结构化输出能力；
- 类型化请求配置 ID 与版本；
- 隐藏、退役和来源缺失状态。

每个能力通道取值为 `supported`、`unsupported` 或 `unknown`，同时记录 `declared`、
`accepted`、`verified` 等证据级别。最终 `supported` 必须来自产品/Endpoint 专属权威声明
或成功的受控验证；接口接受了 Payload 不等于模型真的使用了该能力。文本调用成功只能
证明文本可用，不能证明视觉、工具或推理可用。推理能力只表示 Endpoint 的推理控制参数
可接受且可观察，不表示系统测量了模型智力或隐藏思维质量。

用户手工填写的能力保留为 `declared_by_user` 提示。它可以让用户显式进行实验，但不能在
没有受控证据时静默变成在用角色所依赖的已验证能力。

业务层只传递推理模式、工具定义、图片输入和输出格式等语义参数，由一个 Provider
Adapter 配置转换成真实协议；只有确实存在差异时才增加少量 Endpoint 模型覆盖。用户不
维护任意 JSON Payload 模板。

上下文限制和稳定能力优先采用目录声明。只有必需信息未知、配置版本变化或模型首次进入
在用角色时，才允许执行极小且无副作用的能力验证。工具验证只能使用本地 No-op 工具，
不得触发外部行动。

### 3.4 缺失与过期模型

刷新失败或返回空列表时不能删除任何模型。只有连续两次成功的权威刷新都未包含某个发现
模型，才将其标记为 `source_missing`，并从正常列表隐藏；“过期模型”视图继续展示原因和
最后发现时间。

模型必须同时满足以下条件才进入受保护清理候选：由目录管理、已缺失至少 30 天、不是
手工模型、没有被任何 Food 或其他消费者引用，而且期间没有生产调用。历史证据继续保留。
首版应要求用户显式执行清理；模型重新出现时可以安全重建。

## 4. 在用 Food 与核心模型

核心模型不能从所有 Food 定义直接推导。没人选择的已启用 Food、草稿、归档 Food、仅有
可见授权的 Food，以及预览操作，都不能触发定时模型调用，也不能影响系统健康。

在用投影绝不能替代“全部引用保护”。未上线 Food 的引用仍然要阻止 Provider/模型被删除，
并保留依赖展示；它们只是不消耗主动验证资源，也不影响首页健康。

### 4.1 在用 Food 投影

Food 只有在已启用、未归档并具有可解析的精确主模型引用时才算已上线；模型当前是否健康
不参与这个生命周期判断。已上线 Food 满足以下任一条件时进入 `ServingFoodIndex`：

1. Runtime 使用的同一套 Food Resolver 在完成生命周期和可见范围检查后，接受它作为某只
   现存 Elfie 当前请求的 Food；即使模型健康问题暂时让执行转到保底粮也仍然计入；
2. 至少一只没有保存主粮选择的 Elfie 正在有效使用常用粮；
3. 保底粮已启用，并且是至少一只现存 Elfie 的最终回退；
4. 在一个较短的直接使用租约内，已授权生产路由确实选择或请求过该 Food；即使模型尝试
   失败也计入，租约初始为 24 小时；预览、验证、基准、测试和 Developer Tool 调用不计入。

Elfie 的在线、离开和离线状态不影响该索引：已经选择粮食的 Elfie 随时可能回来。取消
选择、停用或归档 Food，或者直接使用租约到期后，下一次投影即将它移除。
`ServingFoodIndex` 是带代次号的派生缓存，不能成为第二张人工维护表。
它必须复用 Runtime 的纯 Food 解析策略，同时保留“请求路径”和“实际回退路径”，不能把
选择、可见范围和回退规则另抄成一套 SQL。模型健康可以改变实际路径，但不能把用户当前
请求的 Food 移出在用范围。

### 4.2 按角色收敛核心模型

对每一份在用 Food：

- `primary` 始终是核心模型；
- 已配置的 `fallback` 是保护当前执行路径的核心模型；
- `reasoning`、`vision`、`tool` 只有在 Food 策略声明为必需，或者已授权生产请求在角色
  活跃窗口内尝试过该角色时才进入核心；角色活跃窗口初始为 30 天。

没有使用过的可选角色在第一次真实使用前或使用过程中按需检查，不参加周期性主动验证。
新分配的 Food 立即进入服务投影，不能等待历史日志出现。

核心投影按精确 `(connection_id, endpoint_model_id)` 去重，同时保留全部
`(Food, role, capability_channel)` 原因和最高关键级别。十份在用 Food 引用同一个 Endpoint
时只产生一次普通到期心跳；每个不同的必需能力通道最多再产生一次能力检查，而不是十份重复。

Provider 管理页仍可展示全部精选模型的可用数量，但周期健康任务和首页系统健康只使用
以上按角色收敛后的核心模型集合。

## 5. 证据模型与可用性投影

参与健康计算的模型观测至少包含稳定连接 ID、Endpoint 模型 ID、适用时的 Food ID 和语义
角色、工作负载类型、开始/完成时间、状态、首字延迟、总延迟、Token、类型化错误分类和
配置/目录指纹。绝不保存提示词或回复正文。
错误消息和 Provider 响应片段必须先脱敏，凭据、Header 和用户内容不能进入报告。

证据来源依次包括：

1. 当前 Endpoint 和能力通道的真实生产执行；
2. 显式单模型、单连接或全量验证；
3. 核心模型定时心跳；
4. 不产生模型输出的连通性/认证探测；
5. 永远不能证明当前可用性的目录元数据。

投影按以下门槛顺序计算：

1. 连接或模型生命周期排除；
2. 更新的类型化连接级阻断；
3. 本地模型适用的 Runtime 和安装门槛；
4. 带临时失败迟滞的具体模型、具体能力通道证据；
5. 证据新鲜度，不足时为 `unknown`。

面向模型的状态互斥：

- `available`：存在新鲜成功证据，并且没有更新的阻断；
- `degraded`：存在临时失败或近期混合证据，但仍有可用路径；
- `unavailable`：确定性阻断，或临时失败达到阈值；
- `unknown`：从未检查、证据过期或证据范围不足。

Provider 内部继续分别保存生命周期、可达性和账号状态。Owner 页面只获得 `healthy`、
`degraded`、`unavailable`、`unknown` 或 `disabled`，以及原因码和证据时间。

初始新鲜度策略：

- 可达性证据：5 分钟；
- 生产调用或受控验证成功：24 小时；
- 临时失败：有效到受限重试时间，通常为 5–30 分钟；
- 能力声明：有效到 Endpoint/请求配置指纹变化。

类型化账号阻断采用受限指数退避或由用户显式重试。同一范围内后续可信成功会清除阻断。
凭据、Endpoint、模型别名/Digest 或 Adapter 配置变化时，只失效指纹受影响的证据。

## 6. 节省资源的验证策略

| 触发方式 | 执行内容 | 额外模型调用成本 |
| --- | --- | --- |
| 打开 Provider 页或首页 | 立即读取投影；异步刷新已过期的可达性探测 | 0 |
| 真实生产调用 | 追加证据并刷新具体模型/角色投影 | 0 额外成本 |
| 新建或实质修改连接 | 刷新目录、探测传输/认证并检查一个代表模型 | 1 次极小调用 |
| 在用核心模型 24 小时没有真实流量 | 先检查代表模型，再只检查证据过期的核心模型 | 最少必要次数 |
| 普通“验证” | 复用新鲜证据，只检查过期的可见精选模型 | 仅过期模型 |
| 单模型验证 | 只检查具体 Endpoint 和指定能力通道 | 1 次定向调用 |
| 显式“强制全量验证” | 检查全部已启用可见精选模型，并支持提前终止 | 用户明确授权的全量成本 |

受控文本验证不使用工具、不重试，采用确定性极小提示和 1–8 个输出 Token。每个连接默认
并发为 2。周期任务永远不检查非核心模型。多个调用方共享同一个
`(connection_id, model_id, capability_channel, fingerprint)` 在途验证。

## 7. 错误范围与迟滞规则

Provider Adapter 必须根据结构化响应分类；仅靠错误文字匹配不能把故障扩散到全部模型。

| 证据 | 作用范围与处理 |
| --- | --- |
| 密钥无效/吊销、订阅过期、类型化账单或账号额度阻断 | 立即将当前连接标为不可用，停止剩余批次；连接级阻断覆盖其模型，不伪造逐模型失败 |
| Base URL 无效、协议不兼容或已知 Provider 路由返回确定性配置错误 | 立即标记连接配置无效，修改前不再进入定时重试 |
| 模型不存在、已退役或当前账号无模型权限 | 只标记具体 Endpoint 模型，继续验证其他模型 |
| 限流 | 按返回范围降级到 `retry_at`，永不因此退役模型 |
| 网络错误、超时或 5xx | 单次只降级；10 分钟内连续 3 次失败才判定对应对象不可用 |
| 两个 Endpoint 模型都出现临时失败，或一个模型失败且传输探测也失败 | 升级为连接故障并停止剩余批次 |
| 上下文溢出、请求格式错误、安全拒绝或调用方生成的工具/Schema 错误 | 请求级证据，不改变通用模型健康 |
| 受控能力验证返回不支持 | 只把对应能力通道标为不支持，不影响文本可用性 |

一次成功会清除相同范围的临时失败序列。同一 Provider 产品下，一个连接的错误不能阻断
另一个连接。无法可靠识别为账号级错误时，默认使用最窄的模型或请求范围。
调用方自身生成的错误请求保持中立；但同一个 Adapter 协议错误如果能被受控最小验证稳定
复现，就把对应 Endpoint 请求配置或能力通道标为降级。

## 8. 本地 Ollama 投影

本地可用性在统一模型状态之外增加本地门槛：

```text
Ollama 已安装且健康
+ 精确模型已下载
+ 模型已启用且未隐藏/退役
+ 存在新鲜成功 Endpoint 证据
= 本地模型可用
```

Ollama 已安装并且本地连接已启用时，App Lifecycle 可以按退避策略自动尝试启动一次，
不能循环重启。失败后显示“启动”或“修复”。安装和下载模型始终需要用户显式操作。

本地模型页只展示已安装、推荐和被引用模型。服务已运行但没有模型时显示降级状态，并
提供“下载推荐模型”。Ollama 模型 Digest 或 `latest` 实际指向变化时，必须失效对应能力
与验证指纹。

## 9. 统一查询接口

进程内消费者使用 App 持有的查询 Port，不得在内部调用 Provider Adapter 或 HTTP：

- `get(reference)`：不联网，读取一个投影；
- `get_many(references)`：有界批量读取；
- `ensure(reference, max_age, capability, probe_policy)`：只有调用方明确允许主动探测时，
  才复用或启动一个定向验证。

结果包含精确引用、有效状态、原因码、Provider 状态、证据来源、`observed_at`、
`expires_at`、Endpoint 能力和在用/核心角色。Owner HTTP 接口为管理页面提供同样投影。
真实生成仍然是最终证明，并且必须记录自己的结果。
正常生产执行只做被动读取，然后直接把真实生成作为证据；不能在同一次生成前额外付费做
一遍合成验证。主动 `ensure` 必须有权限、限流和连接级冷却，调用方不能通过任意缩小
`max_age` 强制反复验证。

## 10. 页面投影

Provider 管理卡片保留大面积语义背景色和一个状态徽章，不列模型，也不为每个模型画点。
摘要保持有界，例如：

```text
可用 6/8 · 核心 2/2
```

卡片只按精选可见模型互斥着色：

- 绿色：范围内全部启用模型都有新鲜可用证据；
- 黄色：至少一个可用，但并非全部可用且新鲜；
- 红色：零个模型可用，并且存在新鲜的确定性模型失败或连接阻断；
- 灰色：零个模型可用但证据缺失/过期，或者连接已停用/归档。

模型颜色只出现在模型明细页。隐藏、退役、来源缺失属于文字生命周期标签，不能与健康
颜色竞争。

首页模型健康忽略未使用 Food 和非核心模型：

- 绿色：所有必需的在用核心路径可用；
- 黄色：至少一条在用主路径可用，但另一条必需主路径、可选角色或回退路径没有新鲜可用证据；
- 红色：存在在用 Food，并且所有在用主路径都有新鲜的确定性不可用结果；
- 灰色：没有在用 Food、尚未配置模型，或者在用主路径证据仍然未知。

Provider 卡片中的核心数量统计去重后的 Endpoint 模型；首页健康更严格，统计在用角色
路径。因此同一个 Endpoint 同时承担文本和视觉时，可以出现一条路径健康、另一条失败。
首页只显示“核心路径 4/5 · 本地 1/1 · 远程 3/4”等紧凑数量。颜色必须同时配状态文字和
可操作原因。

## 11. 并发、保留与一致性

- Scheduler 使用租约，保证同一到期验证只由一个进程执行；
- 按需验证使用 Single-flight 去重和有界并发；
- 投影按完成时间和稳定序号排序，并拒绝配置指纹过期的证据；
- Food 选择或生命周期变化时增加 `ServingFoodIndex` 代次，并取消已经不再属于核心的排队任务；
- 清理前必须在同一事务中重新检查引用；
- 原始观测采用有界保留期，长期可靠性只保存不含正文或密钥的聚合。

## 12. 对抗审查结论

| 攻击或故障方式 | 设计约束 |
| --- | --- |
| 所有已保存 Food 都让模型进入核心 | 只有已上线且存在当前路由或短期生产使用租约的 Food 进入 `ServingFoodIndex` |
| 把在用过滤复用到删除逻辑，误删未上线 Food 的模型 | 删除使用全部引用保护；在用范围只控制健康和调度 |
| 新分配 Food 因没有历史日志而漏掉 | 当前选择立即激活，不等待日志 |
| 直接读取 `main_food_id` 忽略可见范围或回退语义 | `ServingFoodIndex` 复用 Runtime 的同一套纯 Resolver |
| 真实生产路由失败，来不及写入成功决策 | 已授权路由尝试也会获得短期直接使用和角色活跃租约 |
| 已分配 Food 回退后被移出核心，导致永远无法自动恢复 | 在用范围独立于当前模型健康，始终保留用户请求路径 |
| Elfie 离线后错误取消模型保护 | Presence 不参与服务范围计算 |
| 预览、基准或 Developer Tool 制造虚假使用 | `workload_kind` 必填，只有生产决策获得直接使用租约 |
| 一次文本调用被当成视觉/工具/推理证明 | 能力证据按通道隔离 |
| 通用模型原生能力泄漏到受限 Provider Endpoint | 通用身份只做归组/展示，最终能力必须有 Endpoint 专属权威 |
| 工具或图片 Payload 被接受，但模型没有真正使用能力 | 保留能力证据级别，只有权威声明或受控证明才能形成最终支持 |
| 手工能力勾选被当成可信 Endpoint 事实 | 只保存为用户声明，在用角色依赖前必须获得受控证据 |
| 一条坏 Prompt 把健康模型变红 | 请求级错误不影响通用健康 |
| 一个账号错误关闭同品牌全部账号 | Provider 级阻断严格限定到具体连接 |
| 通用 403 被误判成欠费 | 只有类型化 Adapter 分类才能扩大范围，未知错误保持最窄范围 |
| 一次超时直接把服务变红 | 必须达到临时失败阈值并结合跨模型证据 |
| 配置轮换后旧验证覆盖新证据 | 使用指纹、完成时间和稳定序号拒绝旧证据 |
| 多个页面或服务重复触发付费验证 | 读取接口保持被动，主动 `ensure` 必须显式并使用 Single-flight |
| 调用方反复设置 `max_age=0` 强制付费验证 | 主动探测需要权限，并执行策略拥有的冷却和限流 |
| 发现失败误删正常模型 | 只有连续成功的权威刷新才能标记缺失 |
| 权威空清单被当成失败，内置模型重新伪装成可用 | 保留账号空权限结论，低优先级来源只显示推荐候选 |
| 第一页成功但后续分页失败 | 不完整分页属于刷新失败，不能推进模型缺失计数 |
| 宽泛或被污染目录进入正常列表 | 产品专属权威、Schema/版本校验和精选展示过滤 |
| 自定义 Endpoint 指向元数据服务或通过重定向泄露密钥 | 出站 URL 策略、显式本地例外且禁止跨 Origin 转发凭据 |
| 超大清单耗尽内存或只信任其中一部分 | 字节/记录限制拒绝整次结果并安全回退，不接受部分权威 |
| 账号阻断后仍全量消耗调用 | 代表模型优先并支持连接级提前终止 |
| 未使用的可选 Food 角色被永久验证 | 可选角色必须被声明为必需或存在近期生产角色使用 |
| 多份在用 Food 引用同一 Endpoint，重复产生付费心跳 | 普通检查按 Endpoint 去重，能力检查按 Endpoint/通道去重，同时保留全部使用原因 |
| 同一 Endpoint 同时承担文本和视觉，文本心跳掩盖视觉故障 | Endpoint 去重后仍保留角色路径和通道专属证据 |
| Ollama 自动恢复循环或静默下载大文件 | 只做一次带退避启动；安装和下载必须显式 |
| 多个应用进程重复执行定时任务 | Scheduler 租约和幂等 Run 标识 |
| 报告无限增长或保存私人内容 | 有界保留、聚合汇总且不保存提示词/回复 |

## 13. 实施入口与验收

开始实现前，必须先修订中英文行为契约，并建立精确的一致性台账，把当前能力与本文目标
分开。实现按可独立验收的顺序推进：

1. Endpoint 模型元数据与类型化请求配置；
2. 稳定生产观测和 `ServingFoodIndex`；
3. 可用性投影与被动/主动查询 Port；
4. 节省资源的调度、提前终止和清理；
5. Provider、首页和 Ollama 页面投影。

验收至少证明：

- 已启用但从未分配、从未使用的 Food 不触发定时验证，也不影响首页健康；
- 分配 Food 后立即激活主模型/回退核心模型，取消分配并在合法租约到期后将其移除；
- 已分配 Food 即使当前不可用也保持核心，使后续证据能够恢复它；当前执行可以暂时使用保底粮；
- 预览和测试流量不能激活核心范围；
- 连接级硬阻断停止批次并被其模型复用，单模型失败不污染兄弟模型；
- 平台级大 `/models` 列表不能替换产品专属精选目录；
- 被动可用性读取不产生外部调用，并发主动检查收敛为一次请求；
- 本地健康同时要求 Ollama Runtime 健康和精确模型已经安装。
