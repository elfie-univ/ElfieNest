# 仓库质量治理

ElfieNest 不依赖某一套测试，也不假设每位贡献者都能记住全部架构。仓库通过多种职责
不同、彼此补强的机制持续维护质量。

## 质量闭环

```text
设计意图
    ↓
版本化契约与 ADR
    ↓
根目录和局部 AGENTS.md 指引
    ↓
类型化边界与聚焦实现
    ↓
测试、Scanner、Lint 与类型检查
    ↓
精确基线与基于基础分支的 CI 棘轮
    ↓
一致性收口与负责人审查
```

这些层次不能互相替代。面向人的架构文档解释当前系统；契约定义规则；局部 Agent
指引把规则带到实际编辑边界；机器检查拒绝可检测的违规；静态分析无法证明的语义
决定由人工审查覆盖。

## 每一层保护什么

| 层次 | 保护内容 |
| --- | --- |
| [当前架构](../architecture/) | 对当前真实系统的可理解地图 |
| [架构契约](../contracts/) | 版本化的所有权、依赖方向、Authority 和边界规则 |
| [架构决策记录](../decisions/) | 已接受重大选择的背景与后果 |
| 根目录和子目录 `AGENTS.md` | 编码 Agent 在实际修改目录中必须执行的规则 |
| 类型、Port 与 Facade | 让非法耦合更难表达的显式边界 |
| 单元、集成与架构测试 | 可观察行为和可机器检查的结构规则 |
| Scanner 与精确基线 | 只接纳已登记历史债务、并只允许债务缩减的棘轮 |
| [一致性台账](../conformance/) | 相对已接受契约的当前临时差距及删除门槛 |
| CI 与负责人审查 | 独立验证，以及自动化无法判断的语义审查 |

## 为什么一个改动不能放松评判自己的门禁

架构敏感的 CI 使用不可变基础提交中的 Scanner 和精确基线检查候选生产代码。普通
产品或迁移改动可以删除已登记违规，但不能新增或改写违规。治理变更与生产变更分开
审查，因此修改契约、Scanner 或架构测试时，不能悄悄让同一批产品代码变得合法。

当历史基线归零时，临时基线和详细一致性台账会被删除；Scanner 和架构测试仍然保留，
并以 deny-all 模式运行。对于这类由基线支撑的规则集，基线被删除表示边界已经全面
强制执行，而不是不再检查。

## 贡献者怎样使用这套体系

1. 阅读修改区域最近的 `AGENTS.md`，以及该区域的当前架构说明。
2. 涉及所有权、依赖、Authority、持久化或其他受保护边界时，阅读对应契约和活跃的
   一致性条目。
3. 完成最小而完整的改动，先运行离改动最近的测试。
4. 只有受保护边界发生变化时，运行直接相关的架构检查。
5. 如实提交验证证据，并保持治理变更与产品或迁移变更分离。

具体命令和测试层级见[测试与质量](./testing)。这套体系的规范性规则位于
[仓库架构治理契约](../contracts/repository-governance)，已接受的设计理由记录在
[ADR-0003](../decisions/0003-architecture-governance-ratchet)。
