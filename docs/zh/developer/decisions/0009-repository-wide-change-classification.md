# ADR-0009：全仓实现变更分类

- **状态：** 已接受
- **日期：** 2026-08-12
- **范围：** 仓库架构治理

## 背景

现有治理棘轮只在架构规则与少数生产根目录下的文件同时变化时拒绝 Pull Request。
Developer Tools、普通脚本、根启动器、测试、可执行文档站文件和非治理 Workflow 不在
这个集合中。这些文件同样可以改变 Runtime、构建、测试或交付行为，因此治理变更仍可
一边修改它们，一边修改评判它们的规则。

这是变更分类缺口，不是 `devtools/` 特例。任何同时落在两种分类之外的新可执行表面，
都会重新形成相同的自我批准路径。

## 决策

治理侧与实现侧的隔离作用于整个仓库。

- 治理侧包括契约、ADR、`AGENTS.md`、架构 Scanner、架构测试和治理 CI 定义。
- 先识别治理文件和普通说明文档，其余所有被跟踪文件都属于实现侧，包括产品包、
  Developer Tools、构建/发布脚本、根 Runtime 与工具链配置、普通测试、可执行
  Manifest、资产、文档站代码和非治理 Workflow。
- 架构 Scanner 与架构测试位于宽泛分类的脚本或测试根目录时，治理身份优先。
- 精确架构 Baseline 保持为实现侧文件；产品迁移可以缩减，治理变更不得编辑。
- 普通说明文档保持中立，并跟随它所描述的行为所属变更类别。
- 分类按路径作用于全仓并默认封闭；新增目录、后缀或可执行表面不能保持未分类，也不能
  使用只命中本次违规者的黑名单。

聚焦架构测试覆盖每种分类的代表文件，并证明治理变更不能混入任何实现侧表面。

## 后果

治理变更不能再把产品、开发、构建、测试或交付行为藏在原生产根目录之外。新增可执行
表面除非属于明确识别的治理文件或普通说明文档，否则自动归入实现侧。产品变更仍可
携带普通说明文档，也可以缩减旧 Baseline，而不会被误判成治理变更。

被拒绝的方案包括：建立 `devtools` 黑名单、只保留历史上的六个生产根、主要依靠文件
后缀分类，以及把所有文档文件都视作实现源码。
