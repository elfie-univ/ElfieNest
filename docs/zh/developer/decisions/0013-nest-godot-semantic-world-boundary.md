# ADR-0013：Nest–Godot 语义世界所有权与事件路由

- **状态：** 已接受
- **日期：** 2026-08-13
- **范围：** Nest 内部所有权、Godot 语义通道和具身世界事件路由

## 背景

系统契约已经区分单只 Elfie 的身体通道与共享 Godot 世界通道，但还不足以约束下一步
Nest 迁移。当前实现把说话、用户消息、碰撞和触觉混在 `InteractionHub` 中；多类
Runtime 事件会先经过每个 Body transport，再做专门处理；经过审查的虚拟世界设计所需
结构化视觉、语义行动和环境对象契约也尚不存在。

如果继续只使用早期三个 Nest 领域，同一种跨 authority 流程会被拆散。结构化视觉、
虚拟听觉和语义行动都需要把一只 Elfie 的请求或一次物理发生，与 Nest 拥有的生活含义、
Godot 拥有的物理事实及一个类型化结果关联起来。反过来，若把所有发生都当成同一条广播
流，就会抹掉事实所有权、重复身体感知，并使因果去重无法成立。

## 决策

建立独立的 Nest–Godot 语义世界契约，并把系统契约升级到 1.6。

Nest 有四个内部功能所有者：

1. **空间与设施**拥有 Nest ID、以 Godot 场景发布的稳定物理 ID 为键的无坐标
   家庭目录、设施语义，以及生活规则真正需要的最小离散投影；
2. **巢内生活规则**拥有居民 ID、Home、归属、共享、预约、占用、访问与事件受众规则；
3. **时间与环境**拥有巢内时间、生活阶段、定时环境规则和期望环境状态；
4. **精灵与巢交互**拥有结构化视觉、虚拟听觉和语义行动所需的短期关联与语义拼装。

这些是所有权边界，不要求建立四个 Package、进程、数据库或空目录。稳定 `Nest` Facade
继续作为聚合入站边界。

一套公共 Nest 事件机制横贯四个所有者，但不是第五个业务模块。事实所有者产生事件；
只有需要规则判断时，巢内生活规则才解析受众；路由器把已经确定目标的事件投递一次。
广播只是受众形态，绝不是 Godot Runtime 事件的默认处理。一次物理原因产生的不同事实
使用不同事件类型和 event ID，可以共享一个 cause ID。

一个经过认证的 Godot Gateway 可以承载多条语义线路，但这些线路不能互换：

- 已知目标的身体命令、回执、触觉和本体感知直接在对应 Elfie Body 与 Godot 之间流动；
- 语义行动、结构化视觉、虚拟说话/听见以及环境命令/事实通过窄类型能力跨越 Nest
  语义边界；
- Runtime 就绪、generation、连接和恢复进入 App Lifecycle。

Elfie 仍是自身身体意图的唯一发起者。Nest 可以在原始 intent 授权范围内解析并转发
目标，但不能创建、定时触发或改写 Actor 行为；执行时间或家庭环境规则时，Nest 可以
独立命令世界对象。Godot 继续拥有几何、位置、导航、碰撞、可见性、可听性和实际执行
事实。App 组合真实对象，并在跨 authority 投递时按 ID 找到目标，但不成为语义所有者，
也不成为直接身体流量的强制跳点。

## 后果

仓库新增 Nest–Godot 契约 1.0、双语临时一致性台账、经过审查的迁移规约和对应本地执行
指引。系统契约升级到 1.6，因为共享 Godot 边界和事件路由的语义已经被明确。宏观架构
仍是 v1：不改变根模块、authority 所有者、生产组合根或生命周期所有者。

在后续纵向迁移切片关闭台账之前，当前产品代码有意保持不合规。本治理变更不移动代码、
不修改 Gateway 协议、不建立兼容路径，也不把尚未实现的视觉、行动和环境能力写成现状。

被拒绝的方案包括：继续把交互散落在三个所有者中；把事件、居民、Gateway 或恢复建立
成新的业务模块；让全部 Godot 事件都经过 Nest；让所有语义交互都直接进入 Godot；在
Python 保存坐标或每只 Elfie 的周围列表；以及把每只 Elfie 的渲染相机或 TTS→STT
链路作为 MVP 感知方案。
