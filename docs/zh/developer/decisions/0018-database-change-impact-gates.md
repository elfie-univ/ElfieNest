# ADR-0018：数据库变更必须经过影响盘点与最终状态门禁

- **状态：** Accepted
- **日期：** 2026-08-15
- **范围：** 持久数据库 schema、SQL 语义与持久化边界

## 背景

根 Nest 数据库同时被领养、归属、账户管理、容量、粮食、身体、运行状态、管理投影和
API 夹具使用。一个看似只影响某个 Repository 的改动，可能改变其他地方的计数、权限、
重启行为或精灵记录的含义。

领养流程还暴露出一种具体失败：把进程级中间状态写进最终的 `elfies` 事实表。只给部分
展示查询加过滤，并不能保护配额、容量、触发器、删除和恢复路径。

## 决策

数据库变更由三层独立保护：

1. `infrastructure/persistence/AGENTS.md` 要求变更前完成影响盘点，明确生命周期与失败
   分析，并把数据库工作与产品/UI/运行时改动分开。
2. `scripts/architecture/database_change_scan.py` 提供 schema 对象和 SQL 消费方的只读
   盘点。它是变更前必须执行的第一条审查命令；改动后必须重新执行，确认完整消费面。
3. `test/architecture/test_database_change_boundaries.py` 与现有架构测试共同约束持久化
   边界，拒绝把临时进程状态嵌入最终精灵表。CI 会运行这些测试。

最终业务表只保存持久、完成的事实。临时草稿、租约、生成中间物和重试状态必须放在内存
或明确批准的临时存储中。新增表、字段、索引、约束、触发器、事务边界或 SQL 语义，都
必须评估全部写入方、读取方、派生计数、容量规则、授权路径、运行时投影、测试夹具、
升级路径和回滚路径。`CREATE TABLE IF NOT EXISTS` 不是数据库迁移。

## 后果

数据库变更成为可独立审查的高风险切片。数据库消费方盘点作为人工审查证据，架构测试
负责阻止已知的最终表污染问题。现有不安全的中间状态实现必须先重做才能通过；不能为了
让它通过而削弱门禁。
