# Elfie 精灵内核架构设计

本文档定义单个 Elfie 精灵的核心设计，是后续 `elfie/` 目录下功能实现和重构的架构依据。

`DESIGN.md` 描述的是 Console 前端 UI 设计系统；本文档描述的是具身精灵运行时。后续类似架构设计、模块设计、实现方案类文档，默认使用中文编写，便于持续讨论和维护。

## 设计目标

Elfie 是一个具身 AI 生物，不只是聊天代理。它的每一次回应，都应该由身体状态、情绪化学、记忆、物理限制和当前环境共同塑造。

核心设计目标：

- LLM 只扮演大脑皮层，不等于整个精灵。
- 情绪、能量、睡眠、记忆、上下文组装必须保留在 LLM 外部。
- 所有动作都必须经过身体能力和形态学约束校验。
- Godot 3D 运行和纯终端仿真共享同一套精灵内核逻辑。
- 新功能优先扩展明确的子系统，不把临时逻辑堆进主循环。

## 架构模型

概念上，Elfie 使用三层生物模型：

1. 大脑皮层：高级认知、语言、计划、注意力调度。
2. 边缘系统与核心系统：情绪、能量、睡眠、记忆、上下文组装。
3. 身体与接口：传感器、执行器、反射弧、解剖结构、物理限制。

工程实现上，`elfie/elfie_individual.py` 将精灵聚合为四层：

1. 认知层：`NeocortexBrain`。
2. 核心系统层：丘脑、下丘脑、杏仁核、记忆系统。
3. 神经交互总线层：传感器、信号过滤、语音、动作、碎碎念、物理限位。
4. 身体物理层：解剖结构、关节、步态、脑干反射弧。

这两个模型不冲突。三层模型解释“精灵是什么”，四层模型解释“代码怎么分边界”。

## 当前运行流

当前主要具身闭环是 `ElfieIndividual.perceive_and_respond()`。

```text
原始传感器 / 用户消息 / Godot 事件
  -> 睡眠闸门
  -> 脑干反射检查
  -> 感官噪声过滤
  -> 丘脑上下文组装
  -> 大脑皮层决策
  -> 形态学与物理限位拦截
  -> 语音合成与动作驱动
  -> 能量扣减
  -> 情绪正/负反馈
  -> 情景记忆写入
```

LLM 认知之前有两条快速路径：

- 睡眠闸门：如果下丘脑判断精灵正在睡眠，主循环只返回睡眠碎碎念，不调用大脑皮层。
- 脑干反射：强撞击或舒适抚摸可以直接更新关节、情绪、发声和记忆，不等待皮层推理。

标准认知路径依赖两个类型化数据契约：

- `BrainContext`：边缘系统/核心系统传给大脑皮层。
- `BrainDecision`：大脑皮层传给执行层。

后续功能应尽量维护这些契约，避免让无结构的 `dict` 贯穿整个系统。

## 目录职责

### `elfie/elfie_individual.py`

负责精灵对象聚合和顶层具身闭环。

它应该做编排，不应该承载具体子系统细节。一个新行为如果超过少量胶水逻辑，就应该放到 `brain/`、`body/` 或 `interface/` 的对应子模块里。

### `elfie/brain/`

负责认知，以及会影响认知的内部状态。

- `brain_types.py`：大脑与执行层共享的类型化数据契约。
- `context_builder.py`：丘脑上下文组装。
- `cognition/`：大脑皮层推理、注意力网络、预测加工、性格/配置 prompt 片段。
- `emotion/`：杏仁核式情绪化学，包括衰减、累积、交互、表达映射、情绪输入处理。
- `energy/`：下丘脑式能量、疲劳、睡眠和唤醒逻辑。
- `memory/`：海马体式图记忆、短期感知缓冲、检索、扩散激活、遗忘衰减、情绪加权、记忆巩固、核心认知。

当前 `brain/` 同时包含大脑皮层和边缘/核心系统。现阶段可以接受，因为结构仍然清晰。等模块继续增长、导航开始变困难时，可以考虑做一次不改变行为的目录重组：

```text
brain/
  cognition/
  limbic/
    thalamus.py
    emotion/
    energy/
    memory/
  brain_types.py
```

在公开导入路径和测试可以干净迁移之前，不要急着做这个移动。

### `elfie/body/`

负责身体数字孪生。

- `anatomy/`：骨架定义、关节、声音 profile、关节限位。
- `actuators/gait.py`：底层步态和关节角生成。
- `reflex/`：可以绕过大脑皮层的脑干反射弧。

身体层不应该调用 LLM，也不应该理解用户聊天。它接收物理刺激或运动意图，输出身体状态。

### `elfie/interface/`

负责精灵和外部世界之间的适配。

- `sensors/`：环境、音频、视觉输入适配。
- `actuators/`：语音、运动、碎碎念输出适配。
- `signal_filter.py`：感官大坝，抑制低价值重复输入。
- `physical_limits.py`：动作执行前的形态学和能力拦截。
- `social_connectors/`：Telegram、WeChat 等外部消息入口。

接口层可以知道外部系统，但在进入认知层之前，应将外部事件翻译成内部契约。

### `elfie/config/`

负责精灵专属配置。

- `personality.yaml`：人格、说话风格、身份素材。
- `capabilities.yaml`：支持的动作和行为能力。
- `system_limits.yaml`：能量、疲劳、物理约束。
- `emotion_expressions.yaml`：情绪到表情的映射。

配置文件只能放占位符或非敏感值。运行时供应商密钥应放在环境变量或已 gitignore 的 runtime 配置里。

## 核心子系统

### 大脑皮层

`NeocortexBrain` 在收到 `BrainContext` 后，决定精灵说什么、做什么。

它包含：

- 通过 DMN、CEN、SN 进行注意力路由。
- 通过 `ExpectationManager` 处理预测误差。
- 根据人格、能量、情绪、记忆和用户消息构造 prompt。
- 从模型输出中解析动作标签，形成 `BrainDecision.action`。

当前模式：

- SN：高突显度打断和威胁响应。
- CEN：用户消息和任务处理。
- DMN_ACTIVE：预测误差触发的主动行为。
- DMN_IDLE：空闲碎碎念和低能耗自我表达。

### 丘脑

`ThalamusContextBuilder` 是传感器/核心系统到大脑皮层之间的上下文总线。

它应该组装：

- 过滤后的感官数据。
- 能量和疲劳。
- 睡眠状态。
- 当前情绪摘要、主导情绪、情绪强度。
- 相关记忆上下文。
- 具身解剖描述。

当前 `SensorData` 仍然比较小。下一阶段设计扩展时，应该加入结构化的视觉、听觉、触觉、空间、社交来源字段，而不是继续把这些信息塞进一段普通文本里。

### 下丘脑

`HypothalamusEnergy` 管理能量、疲劳、睡眠、唤醒和动作成本。

它的关键职责是生理闸门。疲劳或睡眠中的 Elfie 不应该表现成一个永远在线的聊天机器人。

后续模型路由应把 token 使用量和模型成本层级反馈到这个系统，让昂贵思考体现为可见的生理消耗。

### 杏仁核

`EmotionSystem` 管理情绪化学。

它当前支持：

- 多种情绪的 baseline。
- 饱和增长。
- 时间衰减。
- 高频慢化。
- 事件去重。
- Big Five 人格调制。
- 情绪之间的相互作用。
- 表情映射。

首选输入路径是 `EmotionInput`。直接调用 `update_emotion()` 主要是为了兼容旧接口和反射捷径。新的感知管线应尽量先把事件转换为 `EmotionInput`。

### 海马体

`MemorySystem` 是记忆系统门面。

它负责：

- 图存储。
- 短期感知缓冲。
- 情景编码。
- 检索。
- 扩散激活。
- 遗忘衰减。
- 情绪加权。
- 记忆巩固。
- 核心认知。
- 五区域上下文组装。

记忆系统应该提供长期身份连续性。大脑皮层接收记忆上下文，但不直接拥有记忆存储。

### 脑干反射

`SomaticReflexArc` 处理即时身体反应。

当刺激是物理性的、紧急的，反射弧允许绕过大脑皮层。它可以直接更新关节、情绪、发声和记忆。

这条路径必须保持克制。它用于快速具身反应，不用于普通行为脚本。

### 身体与动作

`SomaticAnatomy` 定义当前身体形态。`MotionActuator` 将高层动作意图交给步态引擎生成关节目标，再通过解剖结构限位得到实际角度。

设计规则：

```text
认知层可以请求一个动作；
接口层负责校验这个动作；
身体层决定哪些关节角度在物理上可行。
```

不支持或不可能的动作，应转化为具身反馈，而不是静默成功。

## 数据契约

### `SensorData`

当前字段：

- `temperature`
- `is_network_online`
- `salience_score`
- `has_new_message`
- `user_message`

后续可能扩展：

- `vision`
- `audio`
- `tactile`
- `spatial`
- `social_source`
- `source_event_id`

### `BrainContext`

当前字段：

- `sensors`
- `energy`
- `fatigue`
- `is_sleeping`
- `emotion_state`
- `emotion_mood`
- `emotion_intensity`
- `history_episodes`
- `embodied_anatomy`

规则：这是单次 tick 的上下文包，用完即丢，不应该持久化。

### `BrainDecision`

当前字段：

- `action`
- `speech_text`
- `attention_mode`
- `mutter`

后续可能扩展：

- `emotion_inputs`
- `memory_write_intent`
- `confidence`
- `tool_or_model_trace`
- `expression_hint`

不要提前添加这些字段。只有功能真的需要时再加，并用测试证明下游子系统确实消费了这些字段。

## 功能增长规则

1. 新传感能力先加在 `interface/sensors/`，再通过 `SensorData` 暴露类型化字段。
2. 新情绪反应优先建立 `EmotionInput` 映射，不要直接散落修改情绪值。
3. 新动作应进入动作注册表或能力映射，再接入物理校验和动作生成。
4. 新记忆行为应收敛在 `MemorySystem` 门面后面，让其他模块仍然只面对一个记忆入口。
5. LLM prompt 改动应放在 cognition 或 memory context assembly 内。
6. Godot 传输细节不要进入 `brain/` 和 `body/`。
7. `ElfieIndividual` 只做编排，不做逻辑垃圾桶。

## 推荐实现路线

### Phase 1：稳定架构契约

- 随着决策推进持续扩展本文档。
- 增加测试锁定当前 `BrainContext` 和 `BrainDecision` 契约。
- 明确其他包依赖的公开 import 路径。

### Phase 2：结构化感知上下文

- 用类型化视觉、听觉、触觉、空间子结构替代松散 raw sensor 假设。
- Godot 触觉/碰撞数据也走同一套感知契约。
- 保留现有睡眠闸门和反射快路径。

### Phase 3：动作与能力注册表

- 定义一个由 `capabilities.yaml` 支撑的动作注册表。
- 将注册表连接到 `PhysicalLimitsReflex`、`MotionActuator` 和 prompt 指令。
- 不支持的动作必须产生明确的具身反馈。

### Phase 4：情绪输入管线

- 将文本、音频、图像、触觉、系统事件转换为 `EmotionInput`。
- 只有快速脑干反射继续保留直接情绪更新。
- 表情事件稳定地从情绪状态推导。

### Phase 5：记忆与身份连续性

- 确保重要感官事件进入短期缓冲。
- 将重复经历巩固为更高层级的知识。
- 核心认知只从稳定模式更新，不被单次事件随意改写。

### Phase 6：多精灵与巢穴级行为

- 区分单个 Elfie 的私有记忆和共享巢穴事件。
- 显式建模精灵之间的关系。
- 房间/巢穴编排放在 `elfienest/`，不要塞进单个 Elfie。

## 当前目录评估

当前目录结构可以继续使用。它已经基本映射了目标架构，并且 `test/elfie/` 下也有相应的测试结构。

主要歧义是命名：`brain/` 里同时放了大脑皮层和边缘/核心系统。代码规模还不大时，这个结构可以接受。等后续模块继续增多，再引入 `brain/limbic/` 做聚焦重组。

第二个歧义是 actuator 的归属：`body/actuators/gait.py` 负责物理步态计算，`interface/actuators/motion.py` 负责把高层动作意图适配为身体运动。这种拆分是对的，但后续命名和注释要持续强调：

- body actuator：物理运动数学。
- interface actuator：外部命令/输出适配。

## 非目标

- 不把精灵退化成纯聊天包装器。
- 不把供应商凭证或密钥写入被 Git 跟踪的配置和文档。
- 不允许 LLM 绕过校验幻想不存在的身体动作。
- 不让 Godot 细节污染核心大脑契约。
- 不在行为契约稳定前大规模重写目录结构。

## 后续功能完成标准

一个新的 Elfie 功能完成时，应同时满足：

- 目标层级清楚。
- 跨层数据变化时，同步更新类型化契约。
- 子系统测试覆盖新增行为。
- 行为跨模块时，有跨模块测试覆盖完整路径。
- 纯终端仿真仍然能在无外部服务下运行。
- 如果改变 Godot 行为，需要有清楚的事件契约。
- 如果改变架构边界，需要同步更新本文档。
